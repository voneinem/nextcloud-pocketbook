# Security & Data Safety Checklist: PB Cloud (features 001 and 002)

**Purpose**: Validate that the requirements for TLS, redirects, credentials, app passwords, Login Flow v2 tokens, untrusted server names, atomic downloads, resume, overwrite protection, free-space handling and logging are complete, unambiguous, consistent and testable.
**Created**: 2026-10-21
**Feature**: [spec.md](../spec.md) (001, primary); items tagged `002` check [../../002-manage-server-files/spec.md](../../002-manage-server-files/spec.md) where it extends 001

**Depth**: Standard. **Audience**: reviewer (PR / pre-release). **Scope**: requirements quality only, not whether the code works.
**Sources read**: 001 spec, plan, research (R-3 to R-16), contracts/server-requests.md; 002 spec, research, contracts/server-requests.md; constitution III and IV. Where a requirement exists only in plan, research or contract and not in the spec, the item says so, because a spec-level requirement is what tests and reviewers can hold the product to.

**Note**: This custom checklist is generated by the `/speckit-checklist` command based on feature context and requirements.
**Review Ownership**: This checklist is a reviewer-owned requirements-quality review artifact. Mark an item `[x]` only when the reviewer determines the requirements-quality criterion is satisfied.
**Marker Semantics**: `[x]` means the criterion has been reviewed and satisfied for requirements quality. It does not mean implementation work is complete.

## TLS and Transport Trust

- [ ] CHK001 Does the spec state which trust anchors apply (device CA store, bundled CA file, `custom-ca.pem`), or only that `custom-ca.pem` "extends" trust without saying what it extends? [Gap, Spec §FR-005, Constitution IV]
- [ ] CHK002 Is a minimum TLS protocol version specified, together with the required outcome when a server offers only older versions? [Gap]
- [ ] CHK003 Is the behavior defined when `custom-ca.pem` is unreadable, malformed, empty or holds only expired certificates (refuse everything, ignore the file, or fall back), and how the user learns of it? [Gap, Spec §FR-005]
- [ ] CHK004 Is the risk stated that `custom-ca.pem` sits on storage the app cannot protect (FAT, world-writable), so anyone with write access can widen trust, and does "Settings shows whether a file is loaded" give enough information (for example how many CAs, or a fingerprint) to notice a planted file? [Gap, Assumption, Spec §FR-005, §Assumptions]
- [ ] CHK005 Are untrusted, expired and host-name-mismatch certificates specified as separate requirements, given that FR-006 and SC-003 list one "untrusted certificate" among "eight named problems" while the contract defines three certificate error keys? [Ambiguity, Spec §FR-006, §SC-003, Contract error keys]
- [ ] CHK006 Is "a reader clock far from the real time" quantified (US1 scenario 9) so the rule for reporting a clock problem instead of a certificate error is testable? [Clarity, Spec §US1-9]
- [ ] CHK007 Does "every connection" in FR-005 explicitly include the anonymous calls (status check, Login Flow start and poll) and every write request of 002, not only authenticated reads? [Coverage, Spec §FR-005]
- [ ] CHK008 Are requirements defined for system or environment proxy settings, including whether credentials may be sent to a proxy and whether TLS to the server is still end-to-end verified? [Gap]

## Redirects and Address Handling

- [ ] CHK009 Is the unit of comparison for "a different host" (FR-004) defined as scheme, host and port, in line with the contract's "same https host and port", and is an https-to-http redirect stated as refused without retry? [Ambiguity, Spec §FR-004, Contract intro]
- [ ] CHK010 Are a maximum redirect count and loop handling specified, and are redirect rules defined separately for anonymous requests and for requests with a body (POST in 001, PUT/MOVE in 002)? [Gap]
- [ ] CHK011 Is the rule that every address the server hands out (Login Flow poll endpoint, login URL and returned `server`, hrefs in listings) must be https and same-origin a spec requirement, not only a contract/research rule? [Gap, Spec §FR-003/§FR-004, Research R-4, Contract §9]
- [ ] CHK012 Are validation rules for the typed server address specified (user info in the URL, IP literals, IDN/punycode, ports, sub-paths, trailing slash, length), and does the spec say whether the server-returned `server` may replace the typed address? [Gap, Spec §FR-001, §US1-4]
- [ ] CHK013 Do the edge case "refuses to send credentials to the other host and says so" and FR-008 ("no server addresses in error messages") conflict, i.e. is it specified whether the other host may be named in the message? [Conflict, Spec §Edge Cases, §FR-008]

## Credentials and App Passwords

- [ ] CHK014 Does the spec require the credential file's permissions to be requested and the measured protection to be reported to the user (constitution IV), or does FR-007 only say "honestly"? [Gap, Spec §FR-007, Constitution IV, Security & Data Handling]
- [ ] CHK015 Is "states honestly how and where the app password is stored" measurable, i.e. is the minimum content of the statement listed (plain text, who can read it, valid until revoked, how to revoke)? [Measurability, Spec §FR-007, §US1-10]
- [ ] CHK016 Are sign-out and disconnect requirements defined (erasing the app password, what happens to cached listings, downloads, offline marks and queued items, guidance to revoke on the server)? The spec contains none. [Gap]
- [ ] CHK017 Are requirements beyond one edge-case sentence defined for a revoked or invalid app password: which actions stop, whether repeated 401s are retried, and how repeated failed Tests are kept from tripping the server's brute-force throttling (429, Retry-After)? [Gap, Spec §Edge Cases]
- [ ] CHK018 Is it specified that credentials travel only in an authorization header over verified https, never in a URL, and never on anonymous endpoints? [Gap, Contract intro]
- [ ] CHK019 Are input-handling requirements stated for the manual form: masking of the app-password field, keyboard prediction or clipboard, and whether typed values are kept after a failure or when leaving the screen? [Gap, Spec §FR-001]
- [ ] CHK020 Is "never stores the account password" testable when the user types an account password into the app-password field (US1 scenario 6)? Is it stated what happens to that value after the two-factor failure? [Ambiguity, Spec §FR-007, §US1-6]
- [ ] CHK021 Is it specified that storing a new credential is atomic and failure-safe (storage full, partial write), so a failed save cannot destroy a working credential nor leave a half-written secret? [Gap, Spec §FR-007]
- [ ] CHK022 002: Is the app's own data folder (credentials file, database, log, `custom-ca.pem`) excluded from what the upload picker can select, as a spec requirement rather than a research note? FR-004 lists only empty, unreadable and 4 GiB files. [Gap, 002 Spec §FR-001/§FR-004, 002 Research file-browser section]

## Login Flow v2 Tokens

- [ ] CHK023 Is the login lifetime (20 minutes in research) a spec requirement, with defined outcomes for "approves after it expired" and "Check after expiry"? The edge case names both without stating the result. [Gap, Spec §FR-008, §Edge Cases, Research R-4]
- [ ] CHK024 Are "no longer holds the token" (US1-3), "gone from the reader's storage" (SC-002) and research's "memory only, never written" the same requirement, and is it stated what exactly the test inspects (database, settings, files, logs, memory)? [Consistency, Spec §US1-3, §SC-002, Research R-4]
- [ ] CHK025 Is the state of a pending login defined across app restart, screen-off or sleep, and navigating away? [Coverage, Spec §US1, Research R-4]
- [ ] CHK026 Are requirements defined for starting a second login while one is pending, and for cancel, including the honest statement that cancelling locally cannot invalidate the server-side flow? [Gap, Spec §FR-008]
- [ ] CHK027 Is the displayed login link and QR code treated as sensitive (not logged, not persisted, cleared after use)? FR-008 names tokens but not login URLs, while research R-15 does. [Gap, Consistency, Spec §FR-008, Research R-15]
- [ ] CHK028 Are bounds and validation of the Login Flow answers (size, token format and length, login name, app-password length) stated as testable spec requirements? [Measurability, Contract §9]
- [ ] CHK029 Is the partial-success case defined: approval returned credentials, but the follow-up user-id lookup or Test fails; are the credentials kept, and is the user told? [Gap, Spec §US1-3, Research R-4 step 4]

## Untrusted Server Names and Content

- [ ] CHK030 Are "a limited length" and "characters reserved on the reader's storage" in FR-022 quantified in the spec (research: 120 bytes per component, a named character list, reserved device names, trailing dots and spaces, 4,000-byte total path) rather than only in design? [Clarity, Spec §FR-022, Research R-9]
- [ ] CHK031 Is the required outcome for names differing only in Unicode normalization specified? Research contradicts itself (R-9 step 1 converts to NFC, the implementation note says names are not normalized), and FR-022 and SC-016 are silent. [Conflict, Spec §Edge Cases, Research R-9]
- [ ] CHK032 Do the hostile-name lists agree across US3-11, FR-022, the edge cases and SC-016? SC-016 omits overlong names, reserved device names, normalization variants and planted links. [Consistency, Spec §SC-016, §US3-11, §FR-022]
- [ ] CHK033 Are names that collide with the app's own files (temporary-file pattern, database, credentials, `custom-ca.pem`) and existing links or non-folders inside the download tree (`path_unsafe`) covered by requirements? [Gap, Spec §FR-020, §FR-022, Research R-9]
- [ ] CHK034 Is display safety specified for names shown in lists, details and the path line (control characters, right-to-left override, zero-width characters, extension spoofing)? [Gap, Spec §FR-014]
- [ ] CHK035 Is it specified which type or extension decides whether and how a file is opened (sanitized local name or server-supplied type), and what happens for types the viewer cannot open? [Gap, Spec §FR-015, §FR-020]
- [ ] CHK036 Are the bounds in FR-014 ("MUST bound its size") quantified in the spec for answer size, entries per folder, name length, header size and checksum text, or only in plan and contract? [Measurability, Spec §FR-014, Contract §5]
- [ ] CHK037 Is every use of a server-supplied value defined for the failure case where it is hostile or malformed (size, date, ETag, `Content-Range`, checksum), so the "skip or mark, never fail the whole operation" rule is checkable per field? [Coverage, Spec §FR-014]

## Atomic Downloads and Integrity

- [ ] CHK038 Is "complete" defined for FR-017 when the server provides no checksum and no reliable size (unknown length), and is the residual risk of a size-only check stated? [Gap, Spec §FR-017, Research R-8 step 5]
- [ ] CHK039 Is the checksum policy specified: accepted algorithms, whether the listing value or the response value counts, and the behavior when only unsupported algorithms are offered? [Gap, Spec §FR-017, Research R-8]
- [ ] CHK040 Is a rule stated for a server that sends more or fewer bytes than declared, or a body that grows during transfer (stop, discard, report)? [Gap, Spec §FR-014, §FR-017]
- [ ] CHK041 Do the alternatives "removed or kept out of sight" (US3-3) and "cleaned up or offered for resume" (US3-5) leave a single testable oracle, or do two valid outcomes make the scenarios unfalsifiable? [Ambiguity, Spec §US3-3, §US3-5]
- [ ] CHK042 Is the dependence on an unverified assumption stated and a fallback required: the "never visible to the library" outcome relies on the library ignoring the temporary name (DT-NC-3)? [Assumption, Spec §FR-017, Plan Open point 2]
- [ ] CHK043 Is the guarantee after a real power cut on FAT (non-journaled, rename not physically atomic) stated honestly, and is it clear what SC-006's "simulated power loss" does and does not prove? [Assumption, Spec §SC-006, Constitution III]
- [ ] CHK044 Is the scope of start-up cleanup limited by requirement to files the app created and journaled, so a user's file is never deleted by name pattern? [Gap, Spec §US3-5]
- [ ] CHK045 Are the edge cases "same file downloaded twice or two downloads queued" and "file changes between details and end of download" backed by a functional requirement (outcome, which server version is recorded)? They appear only as edge cases. [Coverage, Spec §Edge Cases]

## Resume and Interruption

- [ ] CHK046 Is "the server's version is unchanged" (FR-018) defined: validator strength (strong ETag only), and the outcome for weak or missing ETags? [Clarity, Spec §FR-018, Research R-8 step 4]
- [ ] CHK047 Is the tension reconciled between automatic continuation after the connection returns (US3-4, SC-006) and "network activity only at start and on explicit user action" (FR-034, SC-010)? Research justifies it as continuing a user-started action, but the spec does not say so. [Conflict, Spec §FR-018, §FR-034, §SC-010]
- [ ] CHK048 Are the limits of waiting and retrying (time, attempts, user cancel while waiting, then paused) spec requirements, not only plan values? [Gap, Spec §FR-018, Research R-8 step 7]
- [ ] CHK049 Are required behaviors for the server's ranged-request answers (range ignored, wrong offset, "range not satisfiable", ETag changed) stated at spec level, not only in research? [Coverage, Spec §FR-018, Research R-8]
- [ ] CHK050 Is resume after app restart or power loss specified (explicit user action? check that the partial file matches the journal; what if something else changed or truncated it)? [Gap, Spec §FR-018, §US3-5]
- [ ] CHK051 Are stall and timeout behavior quantified as requirements (connect time, low-speed limit), and is "resumes or restarts cleanly" measurable? [Measurability, Spec §FR-018, Research R-8 step 12]
- [ ] CHK052 Is "no completed download is repeated needlessly" (US4-8, FR-027) turned into a measurable criterion for an interrupted Update? [Ambiguity, Spec §FR-027, §US4-8]

## Overwrite Protection: Reader

- [ ] CHK053 Is the detection of "changed on the reader" specified at spec level, and is it consistent with SC-009 ("100% of tested cases") given that size-and-mtime on FAT (2 s granularity) can miss a change, which research accepts? Is the accepted residual risk stated? [Conflict, Spec §SC-009, §Assumptions, Research R-10]
- [ ] CHK054 Is handling specified for an existing file at the target path that the app did not create and has no record of? FR-021 covers only a local copy "that the user changed". [Gap, Spec §FR-021, Research R-8 step 6]
- [ ] CHK055 Is a requirement defined for a file created or modified between the conflict check and the final rename? [Gap, Spec §FR-021, §FR-037]
- [ ] CHK056 Is the content of the replace confirmation specified (what is lost: name, size, modified time) together with "no default and no timeout choice", or does US3-10 say only "explicit confirmation"? [Completeness, Spec §US3-10, Research R-10]
- [ ] CHK057 Does FR-037 ("lose or silently overwrite anything, whatever happens") enumerate the operations it covers (download, Update, remove copy, cache eviction, start-up cleanup, credential replacement), so it can be tested rather than only asserted? [Measurability, Spec §FR-037]

## Overwrite Protection: Server (feature 002)

- [ ] CHK058 002: Is it a spec requirement that Replace is unavailable (or held) when the server has no trash? Research implements replace as a delete into the trash followed by a move, while FR-033 only restricts Delete. [Gap, 002 Spec §FR-021/§FR-033, 002 Research R-3]
- [ ] CHK059 002: Are the rules for weak or empty ETags (cannot satisfy `If-Match`, so no replace, rename, move or delete) stated in the spec together with what the user sees? [Gap, 002 Spec §FR-022, 002 Contract §intro]
- [ ] CHK060 002: FR-022 and SC-008 ("100%") depend on the server honoring `If-Match`, `If-None-Match` and `Overwrite: F` (LV-W2, LV-W3, LV-W6, all unverified). Is the required behavior stated for a server that ignores a condition? [Assumption, 002 Spec §FR-022, §SC-008, 002 Research R-3]

## Free-Space Handling and Storage Limits

- [ ] CHK061 Is the safety margin of the free-space check (research: the larger of 8 MiB and 1 %) a spec requirement, or does FR-019 leave "check free space" undefined? [Gap, Spec §FR-019, Research R-8 step 1]
- [ ] CHK062 Do the units agree for the large-file warning: the spec says "100 MB", research says 100 MiB; and is it stated whether it is user-configurable? [Conflict, Spec §Assumptions, Research R-8]
- [ ] CHK063 Is it specified which volume is checked (internal storage versus memory card), how free space is measured on FAT, and what happens when the card is removed? [Gap, Spec §Edge Cases, §FR-019]
- [ ] CHK064 Does SC-008 ("refused before any data is written in 100% of tested cases") conflict with the research case of an unknown size, where only the response can be checked? Is a rule stated for enforcing free space and the 4 GiB limit while streaming? [Conflict, Spec §SC-008, §FR-019, Research R-8 step 1]
- [ ] CHK065 For multi-file work (Update, kept folders), is it specified whether free space is checked once for the total or per file (FR-039 says per file), and what is left after a mid-batch failure? [Gap, Spec §FR-039, Research R-10 step 6]
- [ ] CHK066 When storage fills or turns read-only during a write, are the required outcomes stated (partial file removed, journal state, message), including a failed write to the database or journal itself? [Gap, Spec §FR-023, §Edge Cases]

## Logging and Disclosure

- [ ] CHK067 Are the "never log or show" lists consistent across 001 FR-008, 002 FR-041 and constitution IV? Paths, folder names, share and login URLs, search terms and tokens appear in some but not all. [Consistency, Spec §FR-008, 002 Spec §FR-041, Constitution IV, Research R-15]
- [ ] CHK068 Is there a positive definition of what may be logged (codes, status, counts, sizes, error keys, job numbers) rather than only a denylist? The mechanical check N4 matches field names, so a name logged under another field is not detected. [Measurability, Research R-15, R-16 N4]
- [ ] CHK069 Is it required that third-party diagnostic text (libcurl and TLS error strings, HTTP reason phrases) never reaches logs or screens unsanitized, since such strings contain host names and URLs? 002 FR-040 covers server error text, 001 does not. [Gap, Spec §FR-008, §FR-014, 002 Spec §FR-040]
- [ ] CHK070 Are the log file's location, permissions, size bound, rotation and retention specified, along with whether the user can view, clear or export it? Its storage is world-readable FAT. [Gap, Spec §FR-008, Constitution IV]
- [ ] CHK071 Are debug builds and diagnostic modes required to obey the same logging rules? [Gap, Spec §FR-008]
- [ ] CHK072 Do FR-008 ("no file names in error messages shown to the user") and the 002 dialogs that must name the entry (FR-021 replace confirmation, FR-030 delete confirmation) conflict? Is the line between error messages and confirmation dialogs drawn? [Conflict, Spec §FR-008, 002 Spec §FR-021/§FR-030]

## Cross-Cutting

- [ ] CHK073 Is a threat model documented (hostile or compromised server, network attacker, anyone holding the reader or its storage, hostile file content), and is each requirement above traceable to a threat? [Traceability, Gap, Constitution IV]
- [ ] CHK074 Does each security success criterion state how it is verified (host fake server, real-libcurl TLS test, real server LV-N*, device DT-NC-*), so that "100%" in SC-002, SC-003, SC-006, SC-009 and SC-016 is not read as verified on a real server or device? [Measurability, Constitution IX]
